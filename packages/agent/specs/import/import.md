# Spec: `/import` — study material import (CLI agent)

> **Status:** retroactive specification. The feature was implemented first;
> this spec was written afterwards from the agreed design decisions and the
> current code (`src/agent.ts`, `src/tools/readMaterial.ts`,
> `src/spokes/materialSpoke.ts`). Where the code
> differs from the agreed behavior, the difference is listed under
> *Known deviations* instead of being silently written into the spec.

## Purpose

A student puts photos or text files of their own study material (notes,
textbook pages) into `packages/agent/materials/`, runs `/import`, and can then
run `/quiz` to be tested on that material instead of on web research.

## Scope

**In scope**
- A single `/import` command, no parameters
- Every supported file in `materials/` is processed together, in one model call
- Text files and images (read natively by the model, no separate OCR step)
- The result is stored as research findings so the existing `/quiz` flow can use it

**Non-goals (v1)**
- PDF files
- An explanation step on the imported material (only the quiz is generated from it)
- Web search to supplement the material
- Web/Next.js upload (planned separately; it would reuse `materialSpoke`)
- Selecting individual files (`/import <filename>`)

## Acceptance criteria

### Triggering
- **AC-1** The command triggers when the trimmed message equals `/import`, case-insensitively (`/IMPORT`, `  /import  ` also trigger).
- **AC-2** `/import` is handled before input sanitization and topic classification. It is a local command, not a question to the research pipeline.
- **AC-3** `/import` is not added to the conversation history (`messages`), and neither is its response.

### Reading materials
- **AC-4** Supported file types, matched case-insensitively by extension: `.txt`, `.md` (text, UTF-8) and `.jpg`, `.jpeg`, `.png` (images).
- **AC-5** `.gitkeep` and hidden files (names starting with `.`, e.g. `.DS_Store`) are never sent to the model.
- **AC-6** Unsupported files (e.g. `.pdf`) are skipped; the remaining supported files are still imported.
- **AC-7** A file that fails to read is skipped; the remaining files are still imported.
- **AC-8** If `materials/` contains no supported files, the user gets:
  `No files found in materials/. Add a .txt, .md, .jpg or .png file there first.`
  No model call is made and the scratchpad is unchanged.

### Processing
- **AC-9** All supported files are sent in **one** `materialSpoke` call, because related pages must be processed together. Separate calls would leave `/quiz` seeing only the last file.
- **AC-10** The call uses the user's currently selected model (`currentModel`).
- **AC-11** The `sources` field of the findings is built from the file names by the code, not generated by the model: one entry per file, in the form `user-provided material: <filename>`.
- **AC-12** The model must rely only on the provided material. For hard-to-read material it must report lower confidence rather than fill gaps.
- **AC-18** `materialSpoke` never throws. On an API failure (or if the model returns no structured result) it returns findings with an empty `context`, so the command ends in the AC-14 path and AC-13 cleanup still happens.

> AC IDs are stable: new criteria get the next free number instead of renumbering, so references in tests and commits stay valid.

### Cleanup
- **AC-13** After an import attempt, `materials/` is emptied (except `.gitkeep`) **in every outcome**: success, unusable result, and error. This includes unsupported and hidden files.

### Result
- **AC-14** If the findings have an empty `context`, the user gets:
  `Could not extract usable content from the provided files. Please try clearer photos or different files.`
  The scratchpad is unchanged.
- **AC-15** On success the scratchpad is updated:
  - the findings are **appended** to `findings` (becoming the last element),
  - `topic` = `findings.work`, or `"imported material"` if empty,
  - `subject` = `findings.subject`, or `"general"` if missing,
  - `"imported N file(s)"` is appended to `conversationTopics`, where N is the number of supported files sent.
- **AC-16** On success the user gets the file count, the confidence, and a hint to run `/quiz`:
  `✅ Imported N file(s) (confidence: <level>).` followed by `💡 Type /quiz to generate questions from it.`
- **AC-17** A `/quiz` run right after a successful `/import` generates questions from the imported material.

## Known deviations (code vs. this spec)

| ID | Criterion | Current behavior | Status |
|---|---|---|---|
| D-1 | AC-13 | `clearMaterials()` runs only if `materialSpoke` returns normally. | **Resolved — not a deviation in practice.** `materialSpoke` catches API errors and returns empty findings. The guarantee was implicit; it is now explicit as AC-18 and must be covered by a test. |
| D-2 | AC-2 | If a quiz is waiting for the question count, `/import` is read as the count: `parseInt` fails, so a 5-question quiz starts instead of the import. If a quiz is waiting for an answer, the user gets "Please answer with A, B, C, or D." | Open: is this intended? |
| D-3 | AC-13 | If the folder contains **only** unsupported files (e.g. one PDF), `readAllMaterials()` returns `[]`, the AC-8 branch returns early, and `clearMaterials()` is never called — the files stay. | Confirmed in code |
| D-4 | AC-8 | In the same case the message says "No files found", although files are present; skipped files are only reported in the console, never to the user. | Confirmed in code |
| D-5 | AC-4 | The user-facing messages list `.jpg` and `.png` but not `.jpeg`, which is also accepted. | Cosmetic |

## Open questions

- **Q-2** Should there be size limits (per file / total), given that all images go to the model in one request? Currently there are none.
- **Q-3** Imported content does not pass through the injection/topic classifier. Is that acceptable for a local CLI, and what would change for the web version?
- **Q-4** `/import` appends to findings left over from an earlier topic instead of resetting them. The next research question may then reset the scratchpad as a new topic and drop the imported material. Is that the desired lifecycle?
- **Q-5** Files are sent in `readdirSync` order, which is not guaranteed to be alphabetical on every file system. For multi-page material, page order matters — should files be sorted by name explicitly?
- **Q-6** Should the user be told which files were skipped (unsupported or unreadable), not just the console?
- **Q-7** Text files are labeled with their file name in the prompt (`--- name ---`), images are not. With several images the model cannot tell which page is which file. Should images get a text label before them as well?
- **Q-8** `max_tokens` is 1024 for a single combined extraction. With many pages the structured output may be cut off. Is that enough, or should it scale with the number of files?

## Notes for the test plan

- `MATERIALS_DIR` is computed from `process.cwd()` **at module load time**. Tests must set the working directory (or mock `process.cwd`) **before** importing `readMaterial.ts` — the same class of problem as the DynamoDB client in the web package.
- `clearMaterials()` cannot delete subdirectories (`unlinkSync` fails, the error is logged and skipped). Subdirectories in `materials/` are out of scope for v1.
